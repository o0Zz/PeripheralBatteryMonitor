# 8BitDo provider

Loaded when working under `Providers/EightBitDo/`. Moved out of the root `CLAUDE.md`.

- `EightBitDo/EightBitDoBatteryProvider` covers 8BitDo controllers **in DInput mode only**, on their 2.4 GHz dongle or a cable. Nothing is asked: the controller streams its input report on the gamepad collection (`0x0001/0x0005`; a joystick-usage spec is registered beside it for models that may declare `0x0004`), and byte 14 carries the battery — bit 7 charging, bits 0–6 a percentage. Raw-wire offset, report id included; these collections use numbered reports, so SDL's `data[14]` is the same byte. Accepted report ids are `0x01` (what the Ultimate 2 Wireless streams) and `0x04` (the older models' enhanced report).

  **XInput mode has no battery, and that was established rather than assumed.** On the dongle in XInput mode (`2DC8:310B`) `XInputGetBatteryInformation` answers `BATTERY_TYPE_WIRED`/full whatever the charge, the HID game-controller and vendor (`0xFF7A`) collections send nothing unprompted and fail every `GetInputReport`, and [ascendedent/8bitdo-Linux-Software](https://github.com/ascendedent/8bitdo-Linux-Software) shows from firmware that the vendor channel's report `0x81` is answered by the receiver itself and never forwarded to the pad. So the XInput ids are deliberately absent from the model table: listing one would only be a permanent "unknown battery" entry, the same fake-100% every other tray tool shows for these. The user switches mode on the controller (Ultimate 2 Wireless: hold **B** while powering on; **X** goes back).

  **The handle is opened per poll, not held.** The Ultimate 2 streams at 1000 Hz on its dongle; a held handle fills the driver's queue with a stale backlog between polls, while a fresh one's first report arrives in ~9 ms (measured). The read is bounded at 200 ms in total so a switched-off controller costs one short stall per tick.

  The SF30 Pro / SN30 Pro / Pro 2 / Pro 3 only send the battery after a **GET of feature report `0x06`**, which switches them into SDL's enhanced report — a read with a side effect, so only the models that need it get it. It is sent every poll rather than latched, because a power cycle drops the controller back to its plain report. The Ultimate 2 Wireless and Ultimate 3 need nothing. A collection whose input report is 14 bytes or fewer is refused and named in the log: firmware v1.02 of the Ultimate 2 streams 12-byte reports that carry no battery.

  **Only `0x6012` is verified on hardware** (Ultimate 2 Wireless on its dongle, DInput, 2026-09-28: byte 14 = `0x5B` → 91%). The other ids and the feature-`0x06` step are [SDL's `SDL_hidapi_8bitdo.c`](https://github.com/libsdl-org/SDL/blob/main/src/joystick/hidapi/SDL_hidapi_8bitdo.c), with the byte-14 layout independently matching [rigbat](https://github.com/Skesov/rigbat). Bluetooth-only ids (`0x6100`, `0x6101`) are left out, and a Bluetooth 8BitDo is not read at all yet — it would need the Apple provider's shape (found by the watchers, read over HID).

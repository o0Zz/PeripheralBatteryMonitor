# Providers

Loaded when working under `Providers/`. Moved out of the root `CLAUDE.md`.

- **`Providers/`** — `BatteryProviderRegistry` (ordered `Register(Func<IBatteryProvider>)` + `CreateProviders()`; registration order **is** priority order; the static ctor wires the seven built-ins) plus one folder per device family. **To add a new source, implement `IBatteryProvider` and `Register` a factory** (before the first `BatteryDevice` is created) — no changes to `BatteryDevice`. One instance is created per device, so a provider may cache per-device state. Providers are named after the **transport** they serve, since that is what decides whether one applies at all; each rejects the transports it doesn't serve as its first act, so priority order only decides who wins where several could answer. The families, in priority order: `BluetoothLE/BluetoothLEBatteryProvider` (GATT Battery Service `0x180F` / char `0x2A19`, BLE-only, `supportGattBattery` latch, 30 s connect / 5 s read timeouts, also implements `IDeviceLinkState`); `Bluetooth/BluetoothBatteryProvider` (the level Windows itself publishes, `PROP_BATTERY_LEVEL`, 0–100, either Bluetooth transport — it covers devices with no GATT battery service; **read from the AEP bag first, then from the PnP device nodes of the same container**, see below); `Apple/AppleBatteryProvider`; `Logitech/LogitechBatteryProvider`; `SteelSeries/SteelSeriesBatteryProvider`; `Razer/RazerBatteryProvider`; `EightBitDo/EightBitDoBatteryProvider`.
  `ProviderHid` sits beside them, holding the two helpers a HID-discovered provider needs to reopen its own interface from the property bag. It lives in `Providers/` and not in `Hid/` or `Contracts/` because it is the only layer allowed to depend on both — putting it in either would make one depend on the other and collapse the split those folders exist for.
  **Windows hangs `PROP_BATTERY_LEVEL` in one of two places, and the AEP bag is only one of them.** A Classic headset (issue #8: Jabra Evolve 65 SE, Baseus Bowie MA10s; reproduced here with two no-name BR/EDR headsets) publishes it on a single PnP node, the Hands-Free profile node `BTHENUM\{0000111E-…}` of device class `System`, and the association endpoint's bag stays null for its entire connected life — Windows Settings shows a percentage while the log reads `BluetoothClassic no reading, holding -1 connected (none)`. A BLE device carries it on its `BTHLE\Dev_<addr>` node (verified on a Logi M650, where the bag happened to have it too). So when the bag has nothing, the provider runs `DeviceInformation.FindAllAsync` with `DeviceInformationKind.Device` filtered on `System.Devices.ContainerId` — the AEP's `ContainerId` is the real PnP container for a paired device, the same fact `ReconcileSiblingNames` relies on — and takes the first node in 0..100 with **no filter on device class**. Measured at 4–12 ms for a container of 4–11 nodes, so it runs every poll with no node-id cache; the id is remembered only to log it once. **The node value is not nulled on disconnect, unlike the bag's**: a headset switched off still carries its last percentage there, measured on both Classic devices. That is why the lookup is gated on `System.Devices.Aep.IsConnected` being `true`, and the gate is not optional — without it a device in a drawer reads as alive. The bag stays first because it is cached and kept current by the watcher; the nodes are the fallback, not a second reading of the same thing.
  Note the two Bluetooth providers are *not* two sources for the same thing: the BLE one reads the device directly over GATT, the other reads what Windows already knows. A former fifth provider, `CoarseBatteryProvider`, was deleted because it was a *third* reading of the second one's property (via the `System.Devices.BatteryLife` alias) and misinterpreted it as a 1–4 enum — unreachable in practice, and wrong if reached.
  Alongside it, `HidDeviceSpecRegistry` is the discovery-side companion: `BatteryProviderRegistry` says *how* to read a battery, this says which non-Bluetooth devices exist at all. **Only register a spec for a device with no Bluetooth association endpoint** — a Bluetooth device is already found by the watchers, so registering it here would list it twice. That is exactly why `AppleBatteryProvider`, which also reads over raw HID, registers nothing.
  **`HidDeviceSpec.Matches` enforces that rule itself** by refusing any Bluetooth HID path (`HidInterfaceInfo.IsBluetoothPath`: the path carries the HID-over-BR/EDR service `{00001124-…}` or HID-over-GATT `{00001812-…}` in place of `vid_`). It used to be a convention only, which held while every spec named dongle-only product ids. 8BitDo broke that: one product id — `0x6012` — is the same controller on its dongle, on a cable and over Bluetooth, so an id list alone would have listed a paired controller twice.

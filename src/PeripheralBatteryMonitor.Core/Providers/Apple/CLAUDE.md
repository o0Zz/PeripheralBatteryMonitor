# Apple provider

Loaded when working under `Providers/Apple/`. Moved out of the root `CLAUDE.md`.

- `Apple/AppleBatteryProvider`: Apple "Magic" devices (Mouse/Trackpad/Keyboard) report battery only through a vendor HID **input report id `0x90`** (byte[2] = 0–100), invisible to the WinRT Bluetooth property bag. It enumerates via `HidInterfaceEnumerator.Enumerate` on Apple's vendor ids (`0x004C` over Bluetooth, `0x05AC` over USB), then `HidDevice.OpenForReportRequests` + `GetInputReport` — so it holds **no P/Invoke of its own**; the shared `Hid/` layer is the only place SetupAPI and hid.dll are touched. Devices are matched by Bluetooth MAC (Apple reports the MAC as the HID serial number, read through `HidInterfaceEnumerator.ReadSerialNumber`); a single-Apple-device + Apple-looking-name fallback covers systems where the serial isn't the MAC. Retries the report up to 3× because a GET_REPORT right after wake can fail or return stale data. No extra NuGet dependency.
  Unlike Logitech, these devices are **discovered over Bluetooth** like any other paired device — only the battery *reading* goes over HID — so this provider registers no `HidDeviceSpec`. Note this provider is why `HidInterfaceEnumerator` treats report capabilities as best-effort: it addresses a report by id and never needs the descriptor, so a `HidP_GetCaps` failure must not make the interface vanish from enumeration.
  **A failed read says why, once.** Every device without a reading falls through to this provider, so it stays silent unless the device owns an Apple collection (serial = its address) or has an Apple-looking name. Otherwise it writes one `Apple` line, only when the text changes: how many collections carry the device's address, how many are vendor-defined (usage page `0xFF00`+), and the open / `0x90` error code for each. Issue #9 is why: Boot Camp's `applewirelessmouse.sys` filter republishes the Magic Mouse with a reduced report descriptor, the vendor collection disappears, and the log read exactly like an unsupported device. The serial is read through a **query-only** handle, not the read handle, because under that filter the one remaining collection is the mouse collection Windows opens exclusively — the read handle should then fail with `ERROR_ACCESS_DENIED` (inferred from the generic-desktop measurement in the Core `CLAUDE.md`, not measured on that mouse), and the collection could not otherwise be attributed to the device. Two observations from that report are **not** acted on yet: a sleeping mouse answers `ERROR_NOT_READY` (21) and succeeds a few seconds later, so `READ_ATTEMPTS` back-to-back may all land inside one wake window (spacing them needs a sleep on the UI thread, which the poll tick cannot take); and `buffer[1]` differed between a mouse (`0x04`) and a keyboard (`0x00`), possibly a charging flag — two samples, unconfirmed.

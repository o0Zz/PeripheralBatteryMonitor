# Logitech provider

Loaded when working under `Providers/Logitech/`. Moved out of the root `CLAUDE.md`.

- `Logitech/LogitechBatteryProvider` covers Logitech **LIGHTSPEED** devices that talk to their own USB dongle (verified on the PRO X Wireless headset, VID `0x046D` / PID `0x0ABA`). These are not Bluetooth devices at all — hence the HID discovery path — and Windows exposes no battery for them whatsoever: `PROP_BATTERY_LEVEL` is absent from every one of the device's nodes, and there is no HID-battery node either (both checked directly). Battery comes from **HID++ 2.0** over the vendor collection at usage page `0xFF43` / usage `0x0202` (20-byte reports), at device index `0xFF` (the device behind its own receiver, as opposed to indexes 1–6 on a multi-device Unifying receiver). `Logitech/HidppTransport` is the whole HID++ layer — the framing, the vocabulary and the two root calls in one file — `[reportId][deviceIndex][featureIndex][functionId<<4 | swId][params…]`, replies echo the first four bytes so they can be told apart from the unsolicited notifications arriving on the same interface, and feature **indexes are per-device** so they must be resolved at runtime through the root feature rather than hardcoded. It also exposes `Ping` (root func 1). **The ping's test is that a reply came back, not that the magic byte was echoed.** The transport has already matched the reply to that exact request — device index, feature index, and the function byte carrying our nonzero software id — so a frame reaching `HidppTransport.Ping` is an answer to it by construction, and the echo was the same check a second time. Insisting on it cost a real device: the PRO X 2 LIGHTSPEED answers a root ping with parameters `01 10 00` and no echo anywhere, so every poll declared a headset that had just replied to be switched off and never read it. A missing echo is logged, because it says something about a framing nobody has decoded; it no longer decides anything.
  Which feature carries the battery **varies per device**, so the provider probes a chain and binds to the first that both exists and yields a value, caching `(featureId, featureIndex)` so steady-state polling is one transaction (measured: ~42 ms per poll, ~147 ms for the first resolving read). Order is most-to-least precise: `0x1004` UNIFIED_BATTERY (func 1 → state-of-charge percentage, falling back to its discrete level bitfield — genuinely a coarse four-way enum, so each level maps to a representative percentage: 10/30/60/90), `0x1000` BATTERY_UNIFIED_LEVEL_STATUS (func 0 → percentage, `0` meaning unknown), then the two voltage-reporting ones last because converting volts to a percentage costs accuracy: `0x1001` BATTERY_VOLTAGE and `0x1F20` ADC_MEASUREMENT (both func 0 → `[mV_hi][mV_lo][flags]`, sanity-bounded to 2000–5000 mV) via `Logitech/LogitechVoltageCurve`. That curve is an **approximation** (Solaar's Li-Po discharge table): it is flat between ~3.7 V and ~4.0 V, so a couple of millivolts of noise there moves the result by a percent or two. `Resolve` pings before probing, because otherwise a device that is simply switched off would burn one timeout *per feature* on the UI thread every poll.
  The PRO X is the awkward case that motivated the chain: it implements **none** of the three standard battery features — its feature set is root / featureSet / fwVersion / deviceName / equalizer / sidetone / **`0x1F20`** — so it falls all the way through and binds to `0x1F20` at index `0x06` (`0x0F54` = 3924 mV → 70%).
  **There are three Logitech specs, built in a static constructor, and which one a device belongs to is decided by its framing and by whether it is a receiver.** `HidSpec` is the direct HID++ case above. `CenturionHidSpec` is the newer headsets. `ReceiverHidSpec` is a dongle holding other people's devices. All three are still restricted to verified — or at least published — product ids, but the reason has changed and so has what a wrong id costs.
  - **`CenturionHidSpec` — Centurion, and it is not HID++ in another envelope.** The PRO X 2 LIGHTSPEED (PID `0x0AF7`) answers on usage page **`0xFFA0`** / usage `0x0001`, in 64-byte frames with report id **`0x51`**, and does not speak the `0x11` framing at all. It also **implements no HID++ battery feature** — a root ping and a `getFeature 0x1004` both go unanswered. It answers exactly one fixed vendor command, which is what `CenturionBattery` sends and what `LogitechBatteryProvider.ReadBattery` branches to on this usage page, skipping the ping and the feature chain entirely.

    ```
    request : 51 08 00 03 1A 00 03 00 04 0A  [00 * 54]          (64 bytes)
    battery : 51 0B .. .. .. .. .. .. 04 .. PCT .. CHG ...
                 │                    │     │      └ [12] 0x02 = charging
                 │                    │     └ [10] percent, 0..100
                 │                    └ [8]  tag, must be 0x04
                 └ [1] frame kind: 0x03 ack, 0x05 power event, 0x0B battery
    power   : 51 05 00 03 00 00 XX 00        [6] 0x00 = off, 0x01 = on
    ```

    Offsets are raw-wire, report id included — **no hidapi off-by-one to undo here**, unlike SteelSeries: this collection uses numbered reports, so hidapi keeps byte 0 too and every published capture starts `51`. The answer is not necessarily the next frame, since an ack precedes it and the headset's own power events land on the same collection, so the read loops within one budget.

    **Three independent implementations agree byte for byte** and are cited in `CenturionBattery`: [LiamBateman/logibar](https://github.com/LiamBateman/logibar), the proposed Linux driver [*HID: logitech-headset: add a battery*](https://ratatoskr.run/linux-input/2026/09/17552386/t), and [Latency404/Logitech-G-Tray-Tool](https://github.com/Latency404/Logitech-G-Tray-Tool), which is where the name Centurion comes from.

    **There is no Centurion *transport*, and that is the simplification the working command bought.** There used to be one, carrying the envelope — `[0x51][cplLength][flags][featureIndex][functionId<<4|swId][params…]` padded to 64 — with the HID++ feature layer on top of it, normalised so the decoders would not learn which framing produced them. Nothing ever answered that feature layer, and the one Centurion device anybody has does not implement it, so ~250 lines and an `IHidppTransport` abstraction existed for a hypothetical. Both are deleted. The envelope itself is **confirmed** and recorded above rather than in code: the working request decomposes into it exactly (feature index `0x03`, function 1, software id `0xA`, five undecoded parameter bytes). That decomposition is also why the software id must stay **nonzero** — the headset's own power events arrive carrying feature index 3 like a real answer, and software id 0 is the only thing separating them. The `0x50` addressed variant (G522) is still not implemented: its device address has to be brute-forced across 256 values, and an untested branch reads as supported.
  - **`ReceiverHidSpec` — devices behind a receiver, which *are* now supported.** A LIGHTSPEED or Unifying receiver is one interface carrying up to six peripherals at device indexes 1–6; index `0xFF` addresses the receiver itself, which speaks HID++ 1.0 registers and implements no 2.0 battery feature. That is what used to produce the phantom "unknown battery" entry, and it is why the PID allowlist carried the whole weight. **`LogitechReceiverEnumerator` is a better answer at the right layer: a child device exists only because something answered a root ping at its index *and* implements one of the four battery features.** The receiver is never surfaced. So a receiver id shared across products (`0xC547` ships with the G915 X TKL, the PRO X Superlight *and* the G502 X) stops mattering — nothing names the peripheral from the receiver's id, it asks the device, via feature `0x0005` DEVICE_NAME. **A receiver's collection is `0xFF00/0x0002`, not `HidSpec`'s `0xFF43/0x0202`** — the generic vendor page, long reports at usage `0x0002` and short ones at `0x0001`. That is not a variant spelling: a receiver never publishes `0xFF43` and a directly connected device never publishes `0xFF00`, so the two specs cannot match one interface and registration order between them is not load-bearing (receivers stay first anyway). `ReceiverHidSpec` shipped pointed at `0xFF43/0x0202`, which no receiver publishes, so the whole sweep was unreachable and every receiver-attached device was invisible — confirmed against a reporter's log, where a `0xC547` receiver's `0xFF00/0x0002` collection was "claimed by no spec".
    **A receiver needs *both* of its vendor collections, and holding only the long one is what made every slot read as silent.** `HidppTransport` takes one collection or two — a second `HidppTransport.Open` argument, null for a device on its own dongle — rather than there being a second transport class for the two-handle case: everything but the handle count and the frame choice was the same code twice. Two separate things break with one handle, and each alone is enough:
    - **Root-feature traffic goes out as a short `0x10` frame.** Solaar's `base.write()` picks short for any payload that fits, and [logibar](https://github.com/LiamBateman/logibar), which supports this exact `0xC547` receiver plus the G915 X TKL, sends `[0x10, idx, 0x00, swId, featureId>>8, featureId&0xFF, 0x00]` for `getFeature` and the long `0x11` only for the battery call itself. So the transport frames by *who is addressed*, not by payload size: the root feature short, everything above it long.
    - **The reply can come back on either collection.** logibar accepts `r[0] in [0x10, 0x11]`, and a receiver's "that slot is not connected" answer is a HID++ 1.0 error, which is always short. On Linux one hidraw node carries both; on Windows they are two device paths, so the long-only transport could not hear any of it — and silence is indistinguishable from an empty slot. Both handles are therefore read *together*, via `HidDevice.ReadAny`, and a short reply is republished as a long frame before it leaves, so the feature layer and the battery decoders never learn which collection answered.

    The short collection is found by `HidInterfaceInfo.CollectionGroupKey`, which is what two top-level collections of one USB interface have in common — the `colNN` suffix and the last field of the instance id are the parts that enumerate per collection, everything else pins it to one device in one port. Discovery does that lookup, because it already holds the enumeration, and records the result in the child's bag as `PROP_HID_COMPANION_PATH`; a per-poll read would otherwise need a second setupapi walk to find it again. **A missing short collection is not fatal** — the transport then behaves exactly as the long-only one did, which is what every working device was verified against — but it is logged every time, since it is the difference between a sweep that can hear an answer and one that cannot.

    **The sweep now opens with the receiver's HID++ 1.0 register `0x02` connected-device bitmap**, one short transaction, logged and never branched on. Six silent slots cannot tell "nothing is paired to this dongle" from "we asked the wrong way"; this line can, and it is the first thing to read in the next report.

    The sweep is cached per interface path, and the three cases are cached for different lengths because they cost different things: 15 minutes when it found devices, 60 s when the collection would not **open** (the usual cause is vendor software holding it, which clears on its own), and 5 minutes when it opened and **nobody answered** — the expensive case, six pings each running to the full timeout. It uses one pair of handles for all six pings at a 300 ms timeout, so the worst case is ~1.8 s once per interval. The 80 ms this started with was measured against nothing, and a timeout chosen to bound a UI stall is worthless if it also bounds out the answer — a receiver has to forward the ping over the air before an awake peripheral can reply. Every slot's outcome is logged, silence included: a sweep that finds nothing is the shape of every "my Logitech device is missing" report, and it must not look like a sweep that never ran.
  - **To add another LIGHTSPEED device, add its PID to the spec that matches its framing.** For `HidSpec` it must still sit on the `0xFF43/0x0202` collection and answer at index `0xFF`; for `CenturionHidSpec`, on `0xFFA0/0x0001`; a receiver id goes in `receiverProductIds` and nothing else is needed, because the peripheral behind it is discovered rather than declared. The startup snapshot prints each collection's usage page and usage, so a report tells you which of the three a device belongs to without owning one.
  - **The `0xFF00/0x0001` short-report (`0x10`) collection is supported now, for receivers only**, as the second half of `HidppTransport` above. It was not, on the reasoning that "HID++ 2.0 feature calls work perfectly well over the long collection at indexes 1–6" — an inference nobody had tested, and the log of 2026-09-26 is the evidence against it: three sweeps of a `0xC547` receiver, six silent slots each, with the G915 X TKL in use the whole time. A device on **its own dongle** still needs nothing short: it publishes one collection, answers everything on it, and the PRO X collection rejects report `0x10` outright — that path is hardware-verified and unchanged.
  - **The receiver work is still unverified against hardware here**, and so is the rest below — nobody on this side owns either device. The Centurion battery command is no longer a guess, though: it is three agreeing implementations rather than an inference from Solaar's framing, which is what the earlier feature-layer attempt was. `LogitechProbe` still hex-logs every transaction from the startup snapshot. Treat a wrong reading here as unproven, not as a transport bug.
